# vram-mcp 0.3.0

Coordination between sessions is now atomic, inspectable, and honest about what
it cannot see. Three tools are new. The ten from 0.2.0 keep their names, gain
optional arguments, and return richer results. Several of those results change;
read *Behaviour changes* before upgrading an agent that parses them.

## Upgrading

**Stop every vram-mcp client before upgrading.** Each MCP client session runs its
own server, so this means closing every session that uses vram-mcp, then
reconnecting after the upgrade. A 0.2 server and a 0.3 server must never share
a ledger: the old one takes no advisory lock and has no notion of pending
operations, so it can claim a model while another session is evicting it. That
cannot be made safe from either side; see
[One generation per ledger](../coordination.md#one-generation-per-ledger).

From 0.3.0 on, the ledger records the protocol that wrote it, and a client
refuses a ledger with a newer protocol, so the *next* boundary of this kind will
be detected rather than silent. If something has already gone wrong, follow
[Recovering a shared ledger](../coordination.md#recovering-a-shared-ledger).

Install examples now pin the release:

```sh
uvx --from git+https://github.com/sushiHex/vram-mcp@v0.3.0 vram-mcp
```

## Behaviour changes

- **`pressure` no longer reports `ok` on any platform** (#14). `ok` now requires
  every input it rests on, including non-local memory, and no collector reads
  that yet: NVML does not provide it, and Windows' GPU counters were never
  attributed to one adapter (#2, #10). Without it, driver spill cannot be ruled
  out, so the verdict is `unknown`,
  and `detail` says why. `tight`, `degraded` and `thrashing` still report from
  the evidence they have. Windows has a measured route back (#22).
- **`warm` and `unload` report an `outcome`** (#2, #8). `succeeded` means the
  requested residency was observed afterwards; `refused` means nothing was sent;
  `failed` means Ollama rejected it; `unknown` means it may have reached Ollama.
  The coordination mutation tools share `ok`, `outcome`, `reason`, `detail` and
  `summary`, with shapes fixed by their output schemas (#9).
- **`warm` refuses a zero `keep_alive`**, such as `"0s"`, which 0.2.0 forwarded
  to Ollama as an eviction. Use `unload()`, which applies claim and busy
  protection (#2).
- **Unavailable readings are never fabricated** (#2). Unavailable model and
  process readings are `null`, so `loaded: null` means residency is unknown, not
  empty. An unavailable GPU reading leaves `gpus` empty with `free_mb: null`.
  Every reading carries its source, timestamp and scope under `observations`.
- **One canonical model key everywhere** (#2). `LLAMA3`, `library/llama3` and
  `registry.ollama.ai/library/llama3:latest` are all `llama3:latest` in claims,
  protection, operations and history.
- **`VRAM_MCP_GPU_INDEX` scopes everything** (#2): capacity, processes, activity,
  pressure, trends and eviction. `ensure_free` never borrows another GPU's
  headroom.
- **Uncertain results hold the model.** An `unknown` outcome keeps a 120-second
  pending-operation record, and other sessions are refused that model until its
  `pending_until`. `list_claims()` returns those `operations` (#8). A POST is
  never blindly repeated. This narrows the window for conflicting with a
  request Ollama is still executing; it cannot close it. `retry_count` is the
  length of the current run of abandoned attempts, ended by a definite finish or
  by 24 hours without another (#19).
- **Refreshing a resident model costs nothing** against reservations (#2).
- **Status always reports the ledger** (#21). `vram_status()` and `list_loaded()`
  read it on every call and name an unreadable ledger in their `summary`.

## New

- **`reserve`** records capacity for non-Ollama work. `warm` checks it, and
  `ensure_free` reports it.
- **`history`** queries an audit log of actions, appearances and
  disappearances, with cause attribution. **`trend`** summarizes sampled free
  memory. Both are on by default; `VRAM_MCP_AUDIT=0` turns them off.
- **`by`** on `unload`, `ensure_free` and `warm` labels who acted, in history;
  **`force`** on `warm` skips admission checks, though never a pending operation.
- **`VRAM_MCP_STATE_DIR`** names the directory of the ledger and audit state.
  Clients coordinate only with clients that share it (#23).
- **The ledger protocol marker** (#18), described above.
- **Forward compatibility:** a record written by a newer version under the same
  protocol is honoured and reported as `lifecycle: "unrecognized"`. It is never
  deleted for being unrecognized, and it still expires normally (#13).
- **An opt-in [hardware acceptance harness](../acceptance.md)** drives real
  servers against a real GPU and Ollama (#23).

## Fixes

- Windows: a process contending for a newly created lock file could fail with
  `PermissionError` instead of waiting (#18).
- A lock displaced by a foreign writer is reported as `LockDisplacedError`, both
  before and after the work it guarded (#15). An operation interrupted that way
  no longer leaves the model blocked for the life of the process (#18).
- A non-string timestamp in a hand-edited ledger no longer breaks every ledger
  read (#19).
- Windows process identity takes one bounded query instead of sampling counters,
  cutting collection from 9.05 s to 1.28 s on an RTX 3090 (#10, #11).
- The server announces its own version to clients, not the MCP SDK's.
- MCP 2.x removed the API this server uses, so the dependency is now
  `mcp>=1.10,<2` (#1, #8).

## Known limitations

- `pressure` cannot read `ok`, as above (#22).
- Linux has been tested in CI with mocks, not on hardware.
- Ollama's resident-model list does not say which GPU a model is on, so on a
  multi-GPU host `ensure_free` cannot prove a candidate is on the selected one.
- Coordination is cooperative: requests made to Ollama directly bypass it.

## Validated

Windows 11, RTX 3090 (driver 596.49), Ollama 0.34.4, Python 3.14: all 17
acceptance scenarios pass against the 0.3.0 wheel installed in a clean
environment. CI passes on Python 3.10–3.14, Windows and Linux.
