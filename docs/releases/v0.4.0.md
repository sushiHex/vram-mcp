# vram-mcp 0.4.0

On Windows, `pressure` now reaches a real verdict: it reads `ok` when nothing is
wrong and `thrashing` only when the driver is measured paging VRAM. Status is
also fast there, and vram-mcp is now published on PyPI.

```sh
uvx vram-mcp@0.4.0
```

## Added

- **Driver paging is measured on Windows** ([#22](https://github.com/sushiHex/vram-mcp/issues/22)).
  A sampler started with the server reads, once a second, how long WDDM's video
  memory manager (the System process) keeps the selected GPU's engines busy.
  `pressure` reads `thrashing` when that time reached 5% of an engine for at
  least 5 of the last 10 seconds, and the new `pressure.paging` reports that
  window. A status call waits for 5 seconds of history after the server starts
  or the machine wakes, at most about 8 seconds. On the validated
  RTX 3090, overcommitting VRAM by ~3 GB kept it at 5–54% almost every second;
  idle, merely full, or loading a model, it stayed at 0% apart from bursts of a
  few seconds. This is a measured correlation, not a WDDM contract; [#34](https://github.com/sushiHex/vram-mcp/issues/34)
  tracks confirming it beyond one machine.
- **Non-local memory per process and per GPU on Windows** ([#22](https://github.com/sushiHex/vram-mcp/issues/22)).
  vram-mcp reads WDDM's counters for the selected adapter, matched to the NVML
  device by PCI address. Processes WDDM sees on the adapter that NVML does not
  list join the table as `kind: "wddm"`. Observations now carry the device's
  PCI address (`device`), the reason for each uncovered input (`gaps`), and
  device-wide measurements (`totals`).
- **Publishing to PyPI.** A GitHub Release builds the distributions once from
  the tag, attaches them with `SHA256SUMS`, and uploads them to PyPI through
  Trusted Publishing with attestations; every pull request runs the same build.
  See [releasing](../releasing.md).
- **Context-aware, strict and patient loads** ([#47](https://github.com/sushiHex/vram-mcp/pull/47)).
  - `warm(num_ctx=N)` loads at that context. Admission adds a KV-cache
    estimate from `/api/show`, reported as `kv_cache_mb`.
  - `warm(strict_fit=True, num_ctx=N)` checks the whole fit even with nothing
    reserved: size plus KV must fit in free VRAM, minus reservations and
    `VRAM_MCP_FIT_MARGIN_MB` (default 1024). It needs `num_ctx`, and `force`
    can't bypass it.
  - `VRAM_MCP_LOAD_TIMEOUT` (default 110 s, maximum 1800) or
    `warm(timeout_seconds=…)` sets how long a load may take. A load that times
    out reads `unknown` with `reason: "load_timeout"`, and its detail names
    the exception and the elapsed time.
- **Partial fits and load evidence** ([#51](https://github.com/sushiHex/vram-mcp/pull/51)).
  `warm` reports `partial_fit` and `offloaded_mb` when Ollama places part of a
  model outside VRAM (`null` when unknown), plus `started_at`, `elapsed_s`
  and `exception`. Audit events keep these and admission's inputs, as
  numbers and tokens only.
- **Runtimes outside the configured Ollama** ([#49](https://github.com/sushiHex/vram-mcp/pull/49)).
  `vram_status.unmonitored_runtimes` lists model runners on the GPU that no
  loaded model accounts for, and the summary names them.
- **An overcommit acceptance scenario.** `acceptance/harness.py --overcommit`
  fills VRAM, then overcommits it on purpose, measures the paging as bandwidth,
  and checks that `pressure` reads `tight`, then `thrashing`, then `ok`.

## Changed

- **`thrashing` no longer fires on non-local memory.** It used to fire when
  unexplained non-local memory exceeded free VRAM. A full desktop GPU that is
  not paging already meets that, and memory evicted to the backing store is
  not in it at all. Non-local memory is still reported but decides no verdict;
  a full GPU without paging reads `tight`. `pressure.spilling` is replaced by
  `pressure.paging`, and `unexplained_spill_mb` can no longer exceed the
  measured total.
- **`ok` requires paging coverage.** Linux has no paging collector, so
  `pressure` still reads `unknown` there where it would read `ok`, now saying
  why ([#27](https://github.com/sushiHex/vram-mcp/issues/27)).
- **Windows status is about 50 times faster** ([#31](https://github.com/sushiHex/vram-mcp/issues/31)).
  Process names and command lines are read through the Windows API instead of
  PowerShell: ~60 ms instead of 2–3 s per call, and no second PowerShell or
  `wmic` call for runner correlation when models are loaded.
- **`vram_status` returns shorter command lines** ([#35](https://github.com/sushiHex/vram-mcp/issues/35)).
  Each process's command line is cut to its first 160 characters, followed by
  `…`. On the validated desktop that brought a status call from 21.8k to 12.8k
  characters. `vram_status(cmdline_chars=N)` changes the length, `0` leaves
  the field out, and `null` returns them whole.

- **A load whose fit can't be checked is refused** ([#47](https://github.com/sushiHex/vram-mcp/pull/47)).
  `warm` used to allow a new load when free VRAM was unknown, for example
  while `nvidia-smi` hung. It also allowed one when a reservation needed the
  model's size and the size was unknown. Both now refuse and say why;
  `force=True` overrides. A host without working `nvidia-smi` or NVML needs
  `force=True` for every new load.

## Fixed

- **Each server leaked about 165 KB a second on Windows** ([#42](https://github.com/sushiHex/vram-mcp/pull/42)).
  The paging sampler's counter buffers waited for a full garbage collection,
  so a server grew from about 300 MB to over 1 GB of commit in a day. One
  server runs per agent session, so on a desktop with dozens of sessions that
  came to tens of GB. Servers now stay at about 100 MB.
- **Loading a model could fail on its own timeout.** Ollama 0.40 on Windows can
  take more than 10 s to load a model, and it aborts a load when the request
  disconnects. `warm`, `unload` and `ensure_free` now wait up to 110 s for
  Ollama to finish, or up to the configured load timeout, and the operation
  lease outlasts the wait.

- **The audit log no longer stores command lines** ([#38](https://github.com/sushiHex/vram-mcp/issues/38)).
  A non-Ollama process holding at least `VRAM_MCP_MEANINGFUL_MB` was recorded,
  and returned by `history()`, under its whole command line, including any
  credentials passed as arguments. It is now recorded as `<name> (pid N)`.
  Events already in `events.jsonl` keep their old labels.

## Removed

- `VRAM_MCP_SPILL_MB`. It set the non-local floor of the old `thrashing` rule
  and has no meaning now.

## Upgrading

Restart running vram-mcp servers. Clients that read `pressure.spilling` should
read `pressure.paging.sustained`, or simply `pressure.state == "thrashing"`.
On Windows with a free-threaded Python, pin a standard one:

```sh
uvx --python 3.13 vram-mcp@0.4.0
```
